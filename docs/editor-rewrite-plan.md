## 0. The rule

- Every line in the new editor is upstream's unless one of five reasons forces a change: (1) the local dev server owns the file system, (2) simplifications that fall out of watching the file system and treating the editor as a pure client, (3) agent-editable glTF text instead of GLB, (4) one `createGame` for embedding, (5) a bug fix or a better abstraction.
- Anything else needs a line in this file and your mark.

## 3. Feature: the dev server as the file system (reasons 1 and 2)

- [ ] Purpose: every upstream call into the File System Access API keeps working, unchanged, against the dev server. One adapter, no rewrite of the helpers.
- The subset upstream uses (measured, section 1.3 of the upstream facts): `getDirectoryHandle(name, {create})`, `getFileHandle(name, {create})`, `entries()`, `kind`, `name`, `isSameEntry()`, `queryPermission()`, `requestPermission()`, `getFile()`, `createWritable()` then `write()` and `close()`, `File.text()`, `File.name/size/type/lastModified`. Never used: `removeEntry`, `values`, `keys`, `resolve`, `seek`, `truncate`, `showSaveFilePicker`.
- Structures, new file `src/devserver/DevServerSource.ts` (carried over from `CUR` and trimmed to the file, directory, state, events and screenshot calls):
- `interface ProjectFileEntry {path: string; size: number; sha256: string; mtime: number}`
- `interface ProjectReadResult {bytes: Uint8Array; sha256: string}`
- `type ProjectEvent = {type: 'change' | 'add' | 'unlink'; path: string; sha256?: string; client?: string} | {type: 'command'; id: string; command: 'screenshot'; options: ScreenshotOptions}`
- `class ProjectConflictError extends Error {path: string; sha256?: string}` (a 412 from the server)
- `class DevServerSource {clientId: string; list(): Promise<ProjectFileEntry[]>; listDirectories(): Promise<string[]>; createDirectory(path): Promise<void>; read(path): Promise<ProjectReadResult>; write(path, bytes, ifMatch: string | '*'): Promise<{sha256}>; delete(path): Promise<void>; events(listener): () => void; fileUrl(path, sha256?, revision?): string; state(): Promise<{name; versions}>; screenshotResult(id, blob): Promise<void>}`
- Structures, new file `src/devserver/handles.ts`:
- `class ProjectManifest {files: Map<string, ProjectFileEntry>; directories: Set<string>; refresh(): Promise<void>; apply(event: ProjectEvent): void; childrenOf(dir): Array<[name, 'file' | 'directory']>}`
- `class DevServerDirectoryHandle {kind: 'directory'; name; readonly path; getDirectoryHandle(name, {create}); getFileHandle(name, {create}); entries(); isSameEntry(other); queryPermission(); requestPermission()}`. `create` on a directory is `POST /api/directories`. `create` on a file is a `PUT` of zero bytes with `If-Match: *`. A missing entry without `create` throws a `DOMException('NotFoundError')`, which is what `fsApi.ts:29,42` already catch. Permissions answer `granted`.
- `class DevServerFileHandle {kind: 'file'; name; readonly path; getFile(): Promise<File>; createWritable(): Promise<DevServerWritable>; isSameEntry(other)}`. `getFile` is `GET /files/<path>` wrapped as a `File` with `lastModified` from the manifest; it records the `ETag` sha256 on the handle.
- `class DevServerWritable {write(chunk: File | string | Uint8Array | Blob); close()}`: buffers, then one `PUT /files/<path>` with `If-Match: "<sha256 from the last getFile>"` or `*` when the file is new. A 412 becomes `ProjectConflictError`, surfaced by the caller's existing error path.
- Data path, opening the editor: `main.tsx` reads `?t=` from the URL; `new DevServerSource()`; `GET /api/state` gives the project name; `manifest.refresh()` from `GET /api/files` and `GET /api/directories`; `rootHandle = new DevServerDirectoryHandle('', manifest)`; `manager.loadProject({name, path: '', file: 'package.json', handle: rootHandle})`. From there upstream's own `initProjectHandles` (`project.ts:197`), `parsePackageJsonSettings`, `settingsManager.onProjectSettingsChange`, `scriptUtil`, `loadImport` run as written, through the handles.
- Data path, a write: upstream `fsHelper.writeFile(base, path, file)` (`fsApi.ts:84`) calls `getFileHandle` then `createWritable().write().close()` on the adapter; the `PUT` carries `X-Kite3D-Client: <clientId>`; the server broadcasts `change` over SSE to every client; the writer ignores its own client id.
- Data path, a change on disk: chokidar sees it, the server hashes it and broadcasts `change|add|unlink` with `sha256`; `manifest.apply(event)`; then `scriptUtil.changedFilesQ.push(event.path)`. Upstream's queue already accepts a path string (`ScriptUtil.ts:610`), and `refreshChangedFilesQ` (612 to 665) does the rest: `onObserveFileChange` reloads `package.json` or `assets.json`, `scriptFilesChanged` reloads scripts. The main scene changing on disk reloads it with a confirm when dirty (port of `CUR` V:1382 to 1394).
- Lifecycle: one `DevServerSource` and one `ProjectManifest` per page, created in `main.tsx`; the SSE subscription opens in `ViewerInstanceManager.initialize()` and closes in `dispose()`. Handles are cheap value objects created on demand; nothing caches `File` objects. `FileSystemObserver`, the 2 s poll, `BroadcastChannel`, `FetchProxy` and `FileTracker` are gone. Asset URLs resolve through the engine's `createProjectAssetURLModifier` added to the viewer's importer (as `createGame.ts:144` does), so `/kite3d/@id/f.ext` and `/kite3d/<path>` load from `/files/`.
- Server side stays as it is on the cleanup branch: token in header, cookie per port or `?t=` on GET; `GET /api/files`; `GET|POST /api/directories`; `GET /api/state`; `GET /api/events`; `GET|PUT|DELETE /files/*` with `ETag`, `If-Match`, atomic temp-and-rename, import rewriting for `.m?js` with `?v=`; `GET /kite3d/plugins/*`; the screenshot pair.
- Evidence: open a scratch project headless; Files lists every file and empty folder; New Folder, New Script and New Scene create files on disk; a script edited on disk with a shell shows in the editor within a second and its component reloads; an external edit of the open scene prompts and reloads; two editors on the same project: a save in one appears in the other, a stale save gets the conflict message; no request without the token succeeds. Screenshots per case, viewed.

## 5. Feature: Play on the edit viewer with pause and inspection (reason 4)

- [ ] Purpose: upstream's play mode, unchanged in shape: snapshot, run in the same viewer, pause by stopping the clock, click anything in the frozen world, stop reloads the snapshot. Published games and Play share one start routine.
- Structures, engine: `createGame(options)` splits into `createViewer(options): ThreeViewer` and `startGame(viewer, project, {base, onError}): Promise<{stop(): Promise<void>}>`. `createGame` calls both. `startGame` registers scripts and plugins through `registerScripts` (skipping modules already registered on that viewer for the same revision), loads nothing itself when the scene is already attached, resets and starts the timeline, starts components and physics, imports `main.js` and calls `main({viewer})`; `stop` reverses it.
- Structures, editor: upstream `PlayModeHelper` as written (`isRunningMode`, `isPausedRunning`, `startRunMode`, `pauseRunMode`, `unpauseRunMode`, `stopRunMode`). The temp-file path becomes memory: `startRunMode` already exports text glTF in memory (`PlayModeHelper.ts:57,70`); the `resolveFile` fallback at 164 goes.
- Data path, start: `editPreview.start()` hides widgets, gizmo and edit mode; export the snapshot; `unloadScene`; `loadImport` the snapshot; reselect by uuid; `features.enable('physics')`; timeline reset; `startGame(viewer, project, {base: '/files/'})`. Pointer events reach the game while the clock runs.
- Data path, pause: `timeline.stop()`. Rule from issue #23: a paused frame runs no component `update()` and steps no physics; if the entity plugin or the physics plugin keep stepping with the timeline stopped, gate them in the engine. While paused the picker is on: click, inspect, drag with the gizmo, resume from the new position.
- Data path, stop: `startGame().stop()`, physics off, timeline reset, `editPreview.stop()`, reload the in-memory snapshot, reselect. Edits made during play are discarded. Disk is never touched by Play.
- Data path, a script saved during play: `scriptFilesChanged` reloads the module; the helper stops and starts again (`loadRunningScene`, `ViewerInstanceManager.ts:1565`, keeps working with a URL instead of a file).
- Lifecycle: no second viewer, no overlay canvas, no `game` field; the Pause button in `PlayModeButtonGroup.tsx` works as upstream wrote it.
- Evidence: a falling physics box and a script-driven box; Play shows both moving; Pause freezes them (two screenshots a second apart, near-zero diff); click the falling box, the Inspector shows it, drag it, resume, it continues from there; Stop restores the pre-Play frame (diff against the pre-Play screenshot) and the file on disk is byte-identical; a published game still boots through `createGame` in a headless page.
